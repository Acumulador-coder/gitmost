# Синхронизация с Git

[English version](git-sync.md)

Синхронизация с Git зеркалирует пространство в git-репозиторий из Markdown-файлов и держит их
согласованными в обе стороны. Правка страницы в вики превращается в коммит в git, запушенный в
репозиторий коммит превращается в правки страниц. Люди могут в это время продолжать редактировать
те же страницы в браузере: запись из git идёт через слой совместного редактирования и не затирает
того, кто печатает.

У каждого пространства свой репозиторий, его отдаёт по HTTP сам Gitmost. Клон можно открыть в
любом редакторе, в Obsidian или обрабатывать скриптами.

## Как включить

По умолчанию синхронизация выключена. Серверу нужны две настройки:

```env
GIT_SYNC_ENABLED=true
# id пользователя Gitmost, которому приписываются изменения из git
GIT_SYNC_SERVICE_USER_ID=<user id>
```

Без сервисного пользователя сервер с включённой синхронизацией не стартует. Ещё направьте
`GIT_SYNC_DATA_DIR` на постоянный том: там лежат репозитории (по умолчанию
`<DATA_DIR или ./data>/git-sync`, в Docker это вне тома `/app/data/storage`).

Затем администратор пространства открывает **Настройки пространства → Настройки** и включает
**Включить синхронизацию с Git** (на скриншоте английский интерфейс — **Enable Git sync**):

<img alt="Включение синхронизации в настройках пространства" src="screenshots/git-sync-settings.png" width="60%">

Первая синхронизация проходит за несколько секунд и выгружает все страницы пространства. Имя
репозитория — slug пространства (здесь `handbook`).

Пространство, в котором есть страницы с ограничением доступа на уровне страницы, синхронизировать
нельзя: клон показал бы каждую страницу каждому участнику, а push обошёл бы постраничную проверку.
Включение синхронизации для такого пространства завершается ошибкой с этим объяснением.

## Клонирование и push

Репозиторий доступен по адресу `/git/<slug-пространства>.git` на вашем сервере Gitmost. Логин —
email и пароль от Gitmost (HTTP Basic; API-ключи не принимаются, аккаунту с входом через SSO нужен
локальный пароль):

```console
$ git clone https://wiki.example.com/git/handbook.git
$ cd handbook
$ find . -name '*.md' | sort
./Engineering/Code review.md
./Engineering/Engineering.md
./Engineering/On-call.md
./Onboarding.md
./Welcome.md
```

| Ваша роль в пространстве | Что можно |
| --- | --- |
| Может просматривать | clone и fetch |
| Может изменять, Полный доступ | clone, fetch и push |
| Не участник | ничего: репозиторий отвечает 404, как несуществующее пространство |

## Что лежит в репозитории

Каждая страница — один Markdown-файл с именем по её заголовку. Страница с подстраницами становится
папкой с тем же именем, а сама страница — заметкой папки внутри неё: `Engineering` выше — это
`Engineering/Engineering.md`, и её подстраницы лежат рядом.

В файле — id страницы во front matter и тело страницы в Markdown:

```markdown
---
gitmost_id: 01a1312f-d619-7cdd-b37f-8afd50426105
---

The on-call engineer answers pages within **15 minutes**.

| Week | Primary | Backup |
| --- | --- | --- |
| 41 | Alice | Bob |
| 42 | Bob | Carol |
```

`gitmost_id` связывает файл с его страницей, поэтому страница сохраняет себя при переименованиях и
переносах. Не правьте его; у новой страницы просто не пишите его — Gitmost добавит сам.

Детали раскладки:

- Символы, недопустимые в именах файлов (`/ \ < > : " | ? *`), заменяются на `-`; имя обрезается до
  120 символов.
- Две соседние страницы с одинаковым заголовком: ко второй добавляется её короткий id, например
  `Notes ~a1b2c3d4e5.md`.
- Изображения и вложения остаются в Gitmost. Markdown ссылается на них (`/api/files/…`), самих
  файлов в репозитории нет.
- Ссылки на другие страницы — обычные Markdown-ссылки на адрес страницы в вики.
- Коммиты Gitmost делает от имени `Docmost Sync <docmost-sync@local>` с заголовком
  `docmost: export N page(s)`.

## Изменение страниц из git

Коммитьте и пушьте как обычно. Gitmost применяет коммит за несколько секунд:

```console
$ echo "| 43 | Carol | Alice |" >> Engineering/On-call.md
$ printf '# Deploys\n\nWe deploy from `main` every weekday at 11:00.\n' > Engineering/Deploys.md
$ git add -A && git commit -m "On-call: week 43; add Deploys"
$ git push
```

В таблице появляется новая строка, а `Deploys` становится новой подстраницей `Engineering`:

<img alt="Страница и дерево страниц после push" src="screenshots/git-sync-page.png" width="80%">

Что делает в вики каждое изменение в git:

| В git | В вики |
| --- | --- |
| Правка файла | Страница обновляется (сливается с правками из вики, см. ниже) |
| Новый `.md`-файл без `gitmost_id` | Новая страница; заголовок — имя файла, родитель — заметка папки, в которой лежит файл (или корень пространства, если её нет) |
| Переименование файла | Страница переименовывается |
| Перенос файла в другую папку | Страница переезжает под страницу этой папки |
| Удаление файла | Страница уходит в корзину **вместе со всеми подстраницами** |
| Копия файла (два файла с одним `gitmost_id`) | Копия становится новой страницей, оригинал остаётся страницей |
| Прочие файлы (картинки, `.obsidian/`, не-`.md`) | Игнорируются, но остаются в репозитории |

После push Gitmost коммитит обратно то, что изменил сам, например `gitmost_id` новой страницы.
Перед следующим push сделайте `git pull`:

```console
$ git pull
$ git log --oneline
ac4aef6 docmost: export 2 page(s)
5573f53 On-call: week 43; add Deploys
d7adef3 docmost: export 5 page(s)
b6f9a6b init vault
$ head -3 Engineering/Deploys.md
---
gitmost_id: 01a13134-5dc3-79fc-bf35-c49cecc4c876
---
```

Push поверх устаревшего `main` отклоняется как non-fast-forward, как в любом общем репозитории:
сделайте pull, слейте изменения локально и запушьте снова.

## Изменения, сделанные в вики

Каждая правка, новая страница, переименование, перенос или удаление в вики становится коммитом в
`main`, обычно в пределах полуминуты: редактор сохраняет страницу примерно через 10 секунд после
окончания ввода, а каждое пространство проверяется не реже раза в 15 секунд:

```console
$ git pull
$ git log -1 --format='%an <%ae>%n%s'
Docmost Sync <docmost-sync@local>
docmost: export 1 page(s)
$ git diff HEAD~1 -- Welcome.md
@@ -8,3 +8,5 @@
 - [Engineering](#) practices
 - [Onboarding](#) checklist
+
+Questions? Ask in the #handbook channel.
```

## Когда обе стороны правят одну страницу

Gitmost сливает страницу по блокам (блок — абзац, заголовок, список, таблица и т. п.). Блок,
изменённый только с одной стороны, получает версию этой стороны. Если git и вики изменили один и
тот же блок, **побеждает версия из git**, а прежнее состояние страницы сохраняется в истории
страницы — ничего не теряется. Маркеров конфликта, которые нужно разрешать, нет.

Версии, записанные синхронизацией, помечены в истории страницы бейджем **Синхронизация с Git**
(на скриншоте английский интерфейс — **Git sync**):

<img alt="История страницы с бейджем Git sync" src="screenshots/git-sync-history.png" width="80%">

Версия приписывается сервисному пользователю из `GIT_SYNC_SERVICE_USER_ID`, а не автору
git-коммита.

## Ограничения

- Один push может добавить или изменить не больше 10 000 файлов, 16 МиБ на файл, 2 МиБ на
  `.md`-файл и 256 МиБ всего; больший push отклоняется с объяснением. Пока пространство занято
  синхронизацией или одновременно идёт слишком много git-запросов, сервер отвечает 503, и git
  достаточно повторить.
- То, что Markdown не умеет передать, остаётся только в вики: комментарии (в файле остаются только
  их якоря), иконки страниц, порядок соседних страниц, отступы, иконки callout, ширина колонок и
  цвет ячеек таблиц. Правка такого блока из git сохраняет их в вики.
- Свои ключи front matter (например, свойства Obsidian) отбрасываются, сохраняется только
  `gitmost_id`. `[[Вики-ссылки]]` не преобразуются.
- Страница с содержимым, которое конвертер Markdown не может представить, не выгружается; она видна
  в статусе синхронизации пространства (см. ниже) и повторяется в каждом цикле.
- Массовое удаление со стороны вики придерживается: если выгрузка удалила бы больше половины файлов
  (из минимум 4) или оставила бы пространство без страниц, она не удаляет файлы и пишет причину в
  лог. Удаления, запушенные из git, применяются как есть.
- Только один экземпляр сервера: блокировка синхронизации не общая между репликами.

## Для администратора сервера

| Переменная | По умолчанию | Что делает |
| --- | --- | --- |
| `GIT_SYNC_ENABLED` | `false` | Включает синхронизацию (`true` / `false`) |
| `GIT_SYNC_SERVICE_USER_ID` | — | Обязательна при включении: пользователь, которому приписываются изменения из git |
| `GIT_SYNC_HTTP_ENABLED` | как `GIT_SYNC_ENABLED` | Отдаёт репозитории по `/git` |
| `GIT_SYNC_DATA_DIR` | `<DATA_DIR или ./data>/git-sync` | Где лежат репозитории; по одному bare-репозиторию на пространство, имя — id пространства |
| `GIT_SYNC_POLL_INTERVAL_MS` | `15000` | Как часто проверяется каждое синхронизируемое пространство |
| `GIT_SYNC_DEBOUNCE_MS` | `2000` | Сколько собираются события страниц перед синхронизацией |
| `GIT_SYNC_BACKEND_TIMEOUT_MS` | `120000` | Лимит на один процесс `git http-backend` (для fetch — время без вывода) |

Администраторы воркспейса видят состояние каждого синхронизируемого пространства через
`POST /api/git-sync/status` (последний запуск, последняя ошибка, страницы, которые не удалось
выгрузить или применить) и могут запустить синхронизацию сразу через `POST /api/git-sync/trigger`
с `{"spaceId": "…"}`. Метрики `git_sync_cycles_total{result}`, `git_sync_failing_spaces` и
`git_sync_push_failing_spaces` отдаются на порту метрик. Переход пространства в состояние ошибки
пишется в лог один раз как ERROR, восстановление тоже логируется.

Репозитории, созданные сборками до 1.0, обновляются при первой синхронизации: становятся
bare-репозиториями, старая ветка `docmost` удаляется. Файлы старого рабочего дерева остаются на
диске, их можно удалить вручную.
